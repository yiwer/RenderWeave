## 关键结果

- Controller 直接接收原始 UTF-8 bytes；专用 streaming parser 在 databinding 前拒绝 comments、trailing comma/value、single quote、NaN/Infinity、JSON5 与任意层 duplicate key。
- lossless validation tree 保留 decimal 原始 JSON number token；运行时以 BigDecimal 验证 256-byte token、128 precision、normalized scale -64..64，从不经过 binary floating point，也不改写输入。
- 全局预算：每文档 2 MiB、聚合 10 MiB、文档 depth 32、任意单数组 10,000、defined text 65,536 Unicode code points；任一 transport/global 超限整批 413、零部分结果。
- validator 直接解释七种 RenderWeave DSL type 及每一类约束；unknown fields（含 null/object/array）允许，defined present-null 永远失败，类型失败后短路该值的 constraints/children。
- diagnostics 固定为 Schema field order → array index → constraint precedence；instancePath 正确做 RFC 6901 转义，schemaPath 含 exact resolved identity；第 100 条立即停止并置 `truncated=true`。
- Draft target 先通过事务图锁冻结 root-inclusive live revision map，再读取不可变 revisions；Static target 与其子引用均读取精确不可变版本。
- API `/api/v1/root-document-validations` 回显 exact target、root-first dependency set、summary 与每文档结果；OpenAPI 升至 0.5.0，生成 Fetch SDK 通过类型检查。
- PostgreSQL journey 证明 Draft child 使用请求冻结时的 revision；Static root/child 发布后源 Draft 再变化不会改变验证结果。

## 重要取舍

- malformed JSON / duplicate member 无法在一个 JSON transport envelope 内隔离为单文档结果，因此作为 request-level RFC 9457 400；root scalar 等可解析语义错误作为逐文档 validation problem。
- 解析/global budget 失败按 spec 拒绝整批；普通 Schema 违反按文档隔离，不影响同批其他结果。
- `resolvedSchemas` 根节点也包含在内，顺序为 root-first、引用首次出现的 depth-first；与既有 Draft `resolvedRevisions` 的 root-inclusive 语义一致。
- validation module 只依赖 schema public API；不读取 compiled JSON Schema，也没有持久化写能力。
- sample validator UI 仍归 P3/T3-3；本任务已交付 API 与 generated client，不提前建立第二套临时页面状态。
