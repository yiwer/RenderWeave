# Run production OCR as a no-IP Unix-socket sidecar with a frozen offline supply chain

Production OCR leaves the API process and runs as a dedicated sidecar container with no IP networking. The only interface is HTTP/1.1 over a Unix domain socket (`/run/ocr/document-vision.sock`), served by a Python stdlib server; the API connects through a Java AF_UNIX transport that reuses the existing `ProcessRunner` seam, so request/response envelopes, capability probing, limit enforcement and `DocumentObservationIR/1.0` projection stay byte-compatible with the dev/offline stdio adapter. R0 behavior-equivalence is proven by feeding identical requests to both adapters inside the frozen stack and requiring byte-identical responses.

The image is `python:3.12-slim-bookworm` pinned by digest on `linux/amd64`; ARM and Alpine/musl remain inadmissible. The build is fully offline: every wheel is vendored with exact SHA-256 in `requirements.lock`, `pip --no-index --require-hashes` installs from the vendored set, and the three PP-OCRv6-small ONNX models are extracted from the vendored RapidOCR wheel at build time with manifest SHA-256 verification, then mounted read-only. Startup is zero-download: the engine verifies exact RapidOCR/OpenVINO versions and model identities, then must pass a synthetic OCR probe with fixed output before serving; any failure is a startup abort, never a degraded mode.

Two packaging decisions are recorded as deliberate trade-offs. RapidOCR depends on `opencv_python`, whose GUI-linked binaries need libGL/X libraries; rather than vendoring the mesa/X11 closure, the identical-version `opencv-python-headless` binaries overlay the `opencv_python` metadata, leaving the pixel path used by the adapter (`cv2.imdecode` with `IMREAD_COLOR`) unchanged. The `antlr4-python3-runtime==4.9.3` wheel is promoted from the verified PyPI sdist in the fixed builder because the binary-only resolver otherwise selects an incompatible 2.0.0 line. Both dispositions, the license notice bundle and the SBOM-by-lock live in `docker/ocr-sidecar/NOTICE.md` and remain subject to the owner license J1; until that J1 is granted the capability is not admitted and ImageOnlyReadiness stays fail-closed.

Runtime confinement is enforced by the container, not the application: read-only rootfs, non-root UID 10001, all capabilities dropped, no-new-privileges, 2 CPU / 2 GiB / PID 64 / 60 s, OOM scoped to the sidecar, and deterministic single-threaded BLAS/OpenMP environment. Python-level outbound networking is denied before the engine imports. Rollback for the first production version has no pair: an unavailable sidecar projects `DOCUMENT_VISION_UNAVAILABLE` and only closes ImageOnlyReadiness, while the deterministic Schema site remains ready.
